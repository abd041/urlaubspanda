 the CTA requires country selection: CTA → Country modal → Austria / Germany / Switzerland → correct external link If not: CTA → immediate redirect This behaviour should be identical whether the user clicks the normal CTA or the sticky CTA. Future Booking Flow &amp; Technical Requirements At a later stage, the website will be expanded with a fully integrated booking flow directly on Urlaubspanda . Instead of redirecting users to an external partner after clicking: „Termine &amp; Preise anzeigen “ the user should eventually be able to: select dates → choose room / package → enter traveller details → complete the booking directly on our website. The exact booking process and API requirements will be specified later. For the current rebuild, the important point is that the architecture should not block this future development . The CTA and offer data model should therefore be built in a flexible way so that the current behaviour : External Redirect / Country Selection can later be replaced or extended with: Internal Booking Flow without having to rebuild the entire offer page. For example, the offer model could later support different CTA types such as: cta_mode : - direct_redirect - country_selection - internal_booking The frontend components should therefore be reusable and not tightly coupled to external affiliate links. SEO Requirements The entire website must be built with SEO as a core requirement , especially the country landing pages and individual offer pages. Important requirements include : Server- rendered / indexable HTML content Clean semantic HTML structure Correct H1 / H2 / H3 hierarchy Unique SEO title and meta description for every landing page and offer Clean, human- readable URLs Canonical URLs Open Graph metadata for sharing Structured data / Schema.org where appropriate Breadcrumb structured data Hotel / Offer structured data where applicable Image alt texts Internal linking between destinations, categories and offers Sitemap generation robots.txt support Avoid duplicate content caused by filters Filter URLs must be handled carefully for SEO The filter system should remain shareable via URL as described earlier, but we should be able to control whether specific filter combinations are indexable or noindex . We do not want Google indexing thousands of low-value filter combinations. Important destination/category landing pages can instead have dedicated SEO-friendly URLs and content. For example: / oesterreich / / oesterreich /wellness/ / oesterreich / thermenurlaub / / griechenland /all-inclusive/ / aegypten / direkte-strandlage / while temporary combinations such as multiple filters can use query parameters and usually remain non-indexable. Performance The site needs to be very fast , especially on mobile. Performance should be considered from the beginning, including: Optimized responsive images Modern image formats such as WebP / AVIF Lazy loading for images below the fold Preloading of important above-the-fold images Avoid unnecessary JavaScript Code splitting Fast server response times CDN / caching strategy Efficient API calls Pagination or incremental loading of offers No loading of hundreds of deals at once Stable layouts without content jumping The goal should be excellent Core Web Vitals and a fast experience even on mobile connections. General Architecture Goal The new website should be built as a modern, scalable travel platform , not just as a visual redesign of the current site. The foundation should support: Current phase: Landing pages → filters → offer pages → affiliate redirects Later phase: Landing pages → filters → live availability → internal booking flow → booking completion directly on Urlaubspanda So the priorities from day one are: SEO-friendly + very fast + mobile-first + modern + scalable + prepared for direct booking later.
